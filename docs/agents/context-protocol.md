# Context Protocol

How agents persist context, plans, and progress so a future session (or the orchestrator) can resume work without re-exploring the codebase.

## Why this exists

Agents are stateless between sessions. Without structured persistence, every session re-explores the codebase and re-discovers what previous sessions already figured out. This protocol defines how agents save context so a future session can resume without starting over.

## File map

Three categories of files, distinguished by where they live:

**Committed** (version-controlled, shared across all clones):

| File | Purpose |
|------|---------|
| `docs/agents/context-protocol.md` | This file -- the rulebook |
| `docs/agents/issue-tracker.md` | GitHub issue conventions |
| `docs/agents/triage-labels.md` | Label vocabulary mapping |
| `docs/agents/domain.md` | How agents consume domain docs |
| `CLAUDE.md` | Build, test, conventions, gotchas |
| `CONTEXT.md` | Terminology and module ownership |

**Local-only** (`AgentsReport/`, gitignored -- never commit):

| Path | Purpose |
|------|---------|
| `_context/<task>.md` | Shared background for multi-agent tasks (context packs) |
| `<agent>/<YYYY-MM-DD>_<topic>.md` | Incremental progress reports |
| `_plans/<YYYY-MM-DD>_<objective>.md` | Multi-step plan ledgers |
| `SESSION.md` | Resumable session pointer |

**Generated by skills** (ephemeral, not persistent):

- `/verify` output, `/release` changelogs, `/tdd` cycle notes.

## Report format

Every agent report follows this structure:

```
# <Agent> report: <topic>

<TL;DR: status, what was done, what remains, blockers -- 10 lines max>

## Step N: <section title>
<What was done, evidence references, file:line citations>
[DONE] | [PENDING] | [BLOCKED: reason]

## Step N+1: ...

## Handoff
<Status: DOCS_READY | DOCS_PROVISIONAL | DOCS_BLOCKED>
<Detailed handoff fields -- see "Handoff contract" below>
```

Rules:

- Write the TL;DR block immediately when creating the report; update it after every completed step.
- Use `[DONE]`, `[PENDING]`, or `[BLOCKED: reason]` at the end of each step section.
- Cite `file:line` for evidence, e.g. `server/usbip-server/src/server.rs:101` (ConfigOwner). Do not paste large code blocks -- summarize and point.
- Record the actual `/verify` exit code if the gate was run. Never claim verification that was not executed.

## Context packs

When multiple agents need the same background (e.g., an architecture overview, a debugging hypothesis, or a list of files involved in a feature), write a context pack to `AgentsReport/_context/<task>.md`.

A context pack:

- Has a clear scope in its title line
- Contains only the information agents need to begin work (not the full codebase dump)
- Is referenced from reports: "See `AgentsReport/_context/issue-31-metrics.md` for full background"
- Is kept short. If a context pack exceeds 200 lines, split it.

Briefs (from the orchestrator or a previous session) should point at the context pack rather than pasting the entire content inline.

## Plan ledger

For multi-step work, persist the plan to `AgentsReport/_plans/<YYYY-MM-DD>_<objective>.md`.

Format:

```
# Plan: <objective>

## Work items

| ID | Objective | Agent | Depends-on | Scope | Output | Status |
|----|-----------|-------|------------|-------|--------|--------|
| W1 | ...      | ...   | --         | ...   | ...    | PENDING |
| W2 | ...      | ...   | W1         | ...   | ...    | BLOCKED |

## Notes

<Context, decisions, open questions>
```

Status values: `PENDING`, `IN_PROGRESS`, `DONE`, `BLOCKED`. Update the status column as work proceeds; note scope changes in Notes.

## Session resume

When an agent starts a new session, it should check `AgentsReport/SESSION.md` first.

`SESSION.md` format:

```
# Session

Last objective: <what was being worked on>
Current step: <which step is in progress>
Next step: <what comes after>
Active branches/PRs: <branch names and PR numbers, or "none">
Blockers: <open blockers, or "none">
```

If `SESSION.md` does not exist or is stale, the agent starts fresh and creates a new one. Update it at the start of each major step and at session end.

## Handoff contract

When one agent hands work to another, the handoff must carry these minimum fields:

```
Status: <DOCS_READY | DOCS_PROVISIONAL | DOCS_BLOCKED | WORK_READY | WORK_BLOCKED>
Objective: <what was being done>
Evidence: <sources used -- code refs, ADRs, design specs>
Completed work: <what is done>
Affected areas: <files and components touched>
Scope boundary: <what is in-scope for the next agent>
Verification performed: <what was checked and the result>
Remaining uncertainty: <what is not yet resolved>
Recommended next agent: <who should take over and why>
```

The next agent reads this block before doing anything else -- it is the resume point.

## Do's and Don'ts

**Do:**

- Create the report skeleton with TL;DR as soon as you begin work; update it after every completed step.
- Record the actual `/verify` exit code when the gate is run.
- Reference `file:line` for every evidence claim.
- Write context packs when multiple agents share background.

**Don't:**

- Dump all findings into a single massive report at the end.
- Claim verification results without actually running the gate.
- Commit anything under `AgentsReport/` -- it is gitignored by design.
- Paste large code blocks into reports -- summarize and cite paths.
- Leave stale `[PENDING]` markers when the work is done.

## Example report skeleton

```markdown
# Writer report: context-protocol

Status: IN_PROGRESS; produced: docs/agents/context-protocol.md; open gaps: none

## Step 1: Read existing style
Read issue-tracker.md / triage-labels.md; matched conventions. [DONE]

## Step 2: Write protocol
Drafted file map, report format, context packs, plan ledger, handoff contract. [DONE]

## Step 3: Write report
This file. [PENDING]
```
